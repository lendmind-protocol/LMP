---
title: Prepare a signed release
description: Verify, synchronize, tag, and optionally publish an LMP release without accidental checkout mutations.
---

Use `orchestrator/git_release.sh` to prepare a release. The default command is
read-only and prints the manifests it would synchronize. Applying changes,
creating a signed tag, and pushing to the remote are separate explicit steps.

## Review the release plan

```bash
./orchestrator/git_release.sh v0.1.0
```

This validates the version shape and existing Git references without changing
files, commits, tags, or remotes.

## Prepare and sign a release

```bash
./orchestrator/git_release.sh v0.1.0 --apply --tag
```

Before changing versions, the script requires a clean working tree. It then:

1. runs Rust formatting, tests, and release builds;
2. runs the Rust/Node integration check;
3. builds `lmp-sandbox:local` and runs the 38-check qualification matrix;
4. verifies the registry, deployment, and resource gates;
5. synchronizes versions across Rust and Node manifests;
6. creates a Lore-format release commit;
7. runs the 64-scenario real-OSS benchmark with 128 Docker gates against
   that committed release revision;
8. creates a signed Git tag only after the final benchmark evidence passes.

Running the final benchmark after the version-bump commit is intentional: a
clean benchmark must identify the exact revision that will be tagged, rather
than the pre-release checkout.

After the tag is pushed, the GitHub release workflow builds the Linux, macOS,
and Windows archives and verifies that every archive contains exactly the five
expected binaries, has safe top-level paths, and matches `SHA256SUMS`. A local
tag is not release evidence until that hosted matrix has completed.

The packager normalizes gzip and tar metadata, so identical binaries produce
byte-for-byte identical archives. You can verify the current host locally, but
that does not substitute for hosted macOS and Windows builds:

```bash
python3 orchestrator/package_release_artifact.py \
  --target x86_64-unknown-linux-gnu \
  --binary-dir target/release \
  --output-dir lmp-test-results/release-artifacts-local
(cd lmp-test-results/release-artifacts-local && sha256sum *.tar.gz > SHA256SUMS)
python3 orchestrator/release_artifact_gate.py \
  lmp-test-results/release-artifacts-local \
  --targets x86_64-unknown-linux-gnu
```

The tag operation requires a configured Git signing key. If signing is not
available, the command fails rather than silently creating an unsigned
production tag.

## Push after review

```bash
./orchestrator/git_release.sh v0.1.0 --apply --tag --push
```

`--push` requires `--tag` and pushes the current `HEAD` plus the signed tag to
`origin`. Review the generated commit and evidence artifacts before using it.

The release script has no benchmark bypass. Version synchronization and release
preparation always run the complete 64-scenario matrix with Docker enabled.
Missing Docker, qualification, or benchmark evidence is a blocked or failed
release—not a successful one.

The GitHub release workflow runs the same archive gate after downloading the
matrix artifacts. That gate proves archive integrity and contents; it does not
prove that GitHub Actions, a public release, or a downstream download occurred
until the hosted job is actually observed.

## Version scope

The script synchronizes the Rust crate manifests and Node package manifests. It
does not rewrite protected design documents, generated lockfiles by hand, or
unrelated working-tree changes. Cargo is allowed to update its lockfile through
normal workspace resolution after the version change.
