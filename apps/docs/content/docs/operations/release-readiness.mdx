---
title: Release readiness
description: The evidence required before publishing a user-facing release.
---

Do not publish on the basis of a passing unit-test suite alone. A release candidate should have:

- a clean Rust workspace build and test run;
- schema and signature fixtures, including rejection cases;
- end-to-end CLI and MCP smoke tests;
- isolated brownfield benchmark results;
- proof that guidance changes the agent-facing input;
- proof that enforcement changes the final decision;
- documented limitations and known unsupported languages;
- reproducible commands and pinned external sources.

The machine-readable gates must also be complete, not merely present:

- `qualification-result.json` must report `status: "complete"`, exactly 38 of
  38 checks, and `dockerRequired: true`;
- `real-world-benchmark.json` must report `status: "complete"`, exactly 64 of
  64 scenarios, all 128 paired Docker gates passing, all 128 ordinary
  compiler-control checks passing, every provenance source verified, and
  independent reviewer annotations present for a release claim.
- `onboarding-current.json` must contain successful, measured greenfield and
  brownfield runs of `packages/create-lmp/bin.js`, with each run below the
  3,000 ms target and with no source code or secrets in the artifact.

`blocked`, `failed`, `incomplete`, missing, or stale artifacts stop the release
decision. A benchmark that did not build or execute the required Docker image
is not an end-to-end result.

The deployment gate must compare the hosted `registry.json` with the
checked-in index and verify every hosted manifest's SHA-256 digest and
identity/version. A reachable page alone is not deployment proof. The release
archive gate must also verify every target archive against `SHA256SUMS`, reject
unsafe paths, and require exactly the expected binaries.

For the repository-root Vercel project, `vercel.json` pins the install command
to the workspace lockfile and the build command to `@lending-mind/docs`. This
removes monorepo root-detection ambiguity, but it does not prove that a
deployment exists; `verify_static_deployment.py` must still receive HTTP 200
from the configured public URL and validate the hosted registry.

The registry release gate also runs with `--verify-cids`. That mode first
rejects missing or malformed CIDs and then retrieves each CID through a
configured public IPFS gateway. A CID-shaped string without retrievable
content is not release evidence. Every production entry must also carry an
HTTPS `manifestUrl`; this remains the static distribution fallback and is
required even when external CID retrieval is not being exercised locally.

The readiness report also runs `registry_manifest_gate.py` against the Rust
verifier. This binds every index entry to the checked-in manifest bytes,
detached signature, public key, and package identity; metadata-only parity is
not enough. It also compares `registry/registry.json` byte-for-byte with
`apps/docs/public/registry.json`, preventing a stale frontend catalog from
being treated as the current registry.

For a deployment sourced from GitHub, pass `--remote-source origin
--remote-branch main`. The remote-source gate compares the release revision
with the branch Vercel is expected to build. A clean local checkout is not
enough if the deployment branch still points at an older tree.

Daemon resource evidence is validated rather than trusted by its status field:
the report must include numeric RSS and CPU measurements, matching numeric
targets, and at least five seconds of sampling. A hand-written status-only
report is blocked.

Evaluation evidence is independently checked with
`orchestrator/evaluator_artifact_gate.py`. The gate verifies canonical
`lmp:mind:*` and internal `lmp:skill:*` package identities, semantic version,
content digest, lifecycle transitions, limitations, and privacy flags. Use
`--require-clean` for evidence intended to support a release claim; an artifact
that includes source code or raw paths is rejected. The local remediation and
authorization proof can be regenerated with `pnpm verify:evaluator-integration`.

The release candidate also needs a clear boundary around the claim. Show which parts were run against real repositories, which parts used fixtures, which languages were parsed, and which integrations were simulated. A polished demo is useful, but it is not a substitute for a result that another person can rerun.

The release note should state what was proven, what was simulated, and what still requires an independent human adoption pilot.

## One report for the whole decision

Compose the existing gates into one fail-closed report. The command exits with
status `2` until every required local and external evidence item is present;
the JSON output is the source of truth for what remains blocked. Each blocked
check also carries a `boundary` of `local`, `external`, or `human`, making it
clear whether more implementation can close it or whether new authority or
independent evidence is required. It also checks the current checkout itself,
so a clean-looking old artifact cannot hide local changes:

```bash
python3 orchestrator/release_readiness.py \
  --qualification lmp-test-results/qualification-result.json \
  --benchmark lmp-test-results/real-world/real-world-benchmark.json \
  --registry registry/registry.json \
  --deployment https://your-deployed-host.example \
  --expected-registry registry/registry.json \
  --check-manifests \
  --verify-cids \
  --release-artifacts ./release-artifacts \
  --resource-report lmp-test-results/resource-gate.json \
  --onboarding lmp-test-results/onboarding-current.json \
  --human-pilot-report lmp-test-results/human-adoption-pilot.json \
  --require-clean \
  --output lmp-test-results/release-readiness.json
```

Omit an external artifact only when it is not yet available; the report will
mark that check `blocked`, rather than silently treating it as passed. The
current repository intentionally remains pre-release while the deployment,
real IPFS CIDs, cross-platform archives, clean release evidence, and
independent human pilot are still outstanding.

The release workflow applies the same aggregate decision immediately before
publishing archives. It requires `docs/release-evidence/benchmark-review.json`
to contain independent annotations for the measured commit and
`docs/release-evidence/human-adoption-pilot.json` to contain a validated,
redacted adoption report. Neither file is generated by the benchmark itself;
missing inputs fail the workflow rather than being inferred.

## Release decision record

Before publishing, attach one short record containing:

- commit or tag under test;
- Rust, Python, and Node versions used;
- profile identifiers, versions, and digests;
- commands and fixture or repository revisions;
- pass, rejection, and invalid-input examples;
- known unsupported cases;
- the owner for each unresolved issue.

If a check is not complete, write that plainly. "Not tested" is useful release information. It is better than a green summary that makes a reader infer coverage that never happened.
