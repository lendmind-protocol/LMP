# Roadmap and implementation status

This page explains how the implementation currently compares with the
authoritative [project roadmap](https://github.com/lendmind-protocol/LMP/blob/main/ROADMAP.md).
The repository roadmap is the contract; this page is the user-facing status
interpretation. It does not replace the roadmap and does not turn a present
implementation into a completed milestone without evidence.

## How to read the status

| Status | Meaning |
| --- | --- |
| **Verified** | The acceptance boundary has a current, reproducible artifact or test in this checkout. |
| **Implemented, evidence incomplete** | Code exists, but one or more roadmap acceptance tests, fixtures, or reproducibility records are still missing. |
| **Partial** | The capability exists for a bounded path, but the complete roadmap contract is not implemented. |
| **External gate** | Local implementation is present, but completion requires an external service, credential, deployment, pin, or independent person. |
| **Planned** | The roadmap describes the capability, but the implementation is not part of the current product path. |

Passing tests do not automatically graduate a milestone. A milestone is only
complete when its acceptance criteria and its evidence boundary are both met.

## What is verified in this checkout

The following evidence is present and should be treated as bounded evidence,
not as a universal quality claim:

- `lmp-test-results/qualification-result.json` reports `complete`, 38 of 38
  scenarios, with Docker required.
- The Rust workspace has AST, profile compilation, scope resolution, signing,
  evaluation, daemon, MCP, and synchronization crates.
- TypeScript packages provide the CLI, evaluator, schema validation, redaction,
  registry, skill compiler, and MCP-facing compatibility surfaces.
- The docs application builds as a static-first Next.js/Fumadocs portal and
  includes architecture, onboarding, MCP, benchmark, registry, proof, release,
  and versioning references.
- The CLI and evaluator use explicit `pass`, `needs_revision`, `blocked`, and
  error boundaries rather than treating unavailable infrastructure as success.

## Release blockers that remain

These are not wording issues; each blocks a stronger public release claim:

1. **Public registry integrity:** the checked-in packages now have verified
   signatures, public trust keys, and content digests; the production registry
   still needs independently retrievable immutable CIDs.
2. **Release-grade real-world benchmark evidence:** the technical benchmark is
   complete for the current revision with all Docker gates, source verification,
   tool versions, profile digests, and environment metadata retained; a clean
   final release-commit rerun and independent review are still required for a
   publication claim.
3. **Remote distribution:** OCI/IPFS must remain explicitly opt-in until a real
   transport and pinning path is tested. Mock CIDs and placeholder manifests
   cannot be presented as production distribution.
4. **Deployment verification:** the static portal and registry index are
   reachable at [GitHub Pages](https://lendmind-protocol.github.io/LMP/). A
   release claim still requires immutable package manifest retrieval and a
   tagged release run.
5. **Independent adoption pilot:** people outside the implementation loop must
   install, use, remediate, and explain the workflow. Automation cannot replace
   this evidence.
6. **Profile governance:** named-person or organization profiles require
   authorization or must be labeled as community archetypes with provenance and
   no endorsement claim.

## Interaction boundary

Most roadmap work is verified locally and does not require the in-app browser:

- Rust, TypeScript, Python, Docker, CLI, schema, signature, artifact, MCP, and
  benchmark checks use repository commands and test fixtures.
- Documentation pages, navigation, diagrams, playground behavior, and
  responsive layout require browser verification.
- Production deployment and GitHub Actions require external-service inspection.
- The adoption pilot requires independent human interaction.

## Release rule

LMP should not be described as roadmap-complete or released as a fully proven
production protocol while any required artifact is `blocked`, `failed`,
`incomplete`, missing, stale, unsigned, or based only on a fixture. The next
release step is to close the local evidence gaps first, then run the external
deployment and human adoption gates, and publish only the exact claims those
results support.

See [versioning and release notes](/docs/reference/versioning) and [evaluation results](/docs/reference/results) for the operational gates, proof matrix, and benchmark evidence.
